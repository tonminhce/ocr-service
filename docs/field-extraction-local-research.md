# Local OCR and typed field extraction for Vietnamese document bundles

Research checked on 14 October 2026. This is a design and source review, not a claim that the proposed pipeline has been implemented or validated on the user's documents. Research used public documentation and papers only. Private contract and identity images must stay on the user's machine or approved private infrastructure; no paid API or public demo upload is required.

The recommended next step is to keep the Rust API, durable queue, and Rust worker, add a separate extraction strategy beside the existing full-page Qwen transcription, and require source evidence for extracted fields. A rental contract with attached identity cards is a bundle of related documents. Feeding every page into one prompt and asking for one flat JSON object makes party mixing and silent conflict resolution easy. Classify and group pages first, extract candidates within each logical document, then reconcile explicitly in Rust.

Implementation update, 15 October 2026: the default `course_layout_vlm` strategy now runs Rust PP-DocLayoutV3 detection, mask crops, region recognition and formatting, with measured region geometry and raw text. `full_page_vlm` remains an explicit legacy baseline. Neither strategy implements typed business fields, field-to-region evidence, logical document grouping or acceptance decisions. A production extraction result still needs the observed value, source, validation findings and review decision alongside its normalized value. See the [layout report](layout-e2e-report.md).

The following comparison distinguishes document conversion, spatial OCR evidence, and typed business extraction. Language support means a documented capability, not measured accuracy on Vietnamese rental contracts or identity cards.

PP-StructureV3 is an appropriate reference for how to separate layout from text recognition. Its documented pipeline includes independently usable modules and emits OCR and layout information before formatting the document. Layout labels such as text, table, image, or title are not application roles such as landlord, tenant, or identity attachment. Those roles require a separate classification/extraction layer. The documentation also shows ONNX Runtime operation with formula recognition disabled while support is incomplete; consequently, an ONNX export is not proof of full pipeline parity. [Official PP-StructureV3 documentation](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PP-StructureV3.en.md).

PaddleOCR-VL's complete client still runs layout analysis and other workflow stages when its recognition model is served over vLLM. Its ordered `parsing_res_list` blocks are useful evidence units, but a block box may cover an entire paragraph or table; it is not necessarily a word-level box. The current 1.6 research emphasizes refinement of difficult regions. That supports evaluating region-based recognition, but its benchmark headline should not be converted into a promised field accuracy. The original paper's Vietnamese language listing and a new checkpoint's performance on the user's Vietnamese scans are different facts. [Pipeline/client boundary](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md), [1.6 technical report](https://arxiv.org/html/2606.03264v1), [original supported languages](https://arxiv.org/html/2510.14528v1).

GLM-OCR also separates two tasks. Its parsing SDK uses PP-DocLayoutV3 and regional recognition; the official model card directs information extraction users to direct model inference with a specific JSON-shaped prompt. The technical report describes KIE as full-image inference rather than explicit layout cropping. Therefore, direct GLM-OCR KIE is a useful comparison against Qwen, but it still needs independent evidence handling and Rust validation. The SDK defaults and examples include both local and cloud modes: use an explicit local endpoint and configuration, not the cloud quick-start path. [SDK and self-hosting](https://github.com/zai-org/GLM-OCR), [supported prompt scenarios](https://huggingface.co/zai-org/GLM-OCR), [parsing versus KIE](https://arxiv.org/html/2603.10910v1).

Docling's document representation contains document structure and provenance, while `DocumentExtractor` accepts dictionary/Pydantic templates and returns extracted page data. Those are separate capabilities; using both does not automatically link every extracted field to an exact token or box. The official extraction example also demonstrates supplied defaults populating absent data. For this application, defaults such as an ID number, date, or rent amount must never become purported observations: use nullable fields plus explicit missing/unreadable states. [Document representation](https://docling-project.github.io/docling/concepts/docling_document/), [typed extraction and defaults](https://docling-project.github.io/docling/_generated/examples/extraction/).

Docling's current catalog distinguishes layout, OCR, tables, and VLM conversion. Its language behavior follows the OCR engine, and its options allow explicit Tesseract language files rather than treating every engine as multilingual by default. Remote services are disabled by default in pipeline options; an API-based local model can still require that option, so the flag alone is not an egress policy. Restrict the actual endpoint and network access. [Model/engine catalog](https://docling-project.github.io/docling/usage/model_catalog/), [pipeline configuration source](https://github.com/docling-project/docling/blob/main/docling/datamodel/pipeline_options.py).

For a CPU-compatible spatial baseline, Tesseract documents Vietnamese `vie` trained data and TSV/hOCR output containing word positions and recognition confidence. Rust can invoke a bounded local process with fixed arguments and parse TSV; no Python application code is needed. It remains an OCR engine, not a rental-contract field extractor, and a word confidence score is not a probability that a contractual field is correct. Compare it against a Vietnamese-configured Paddle pipeline rather than assuming either wins. [Vietnamese language data](https://tesseract-ocr.github.io/tessdoc/Data-Files-in-different-versions.html), [TSV and hOCR output](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html).

There are two feasible integration choices. With the already accepted external inference-server boundary, the quickest useful layout evaluation is a local Paddle/Docling/GLM SDK adapter returning versioned JSON to the Rust worker. It can expose model inference and geometry only; the queue, job lifecycle, candidate association, validation, review decisions, and external API remain Rust. That adapter is a Python inference component and should be described honestly. It is not a Rust port of PP-StructureV3.

If no Python layout process is acceptable, use exported detector/recognizer models through ONNX Runtime's C API or a community Rust wrapper, then implement the pipeline in Rust. The official ONNX Runtime documentation labels Rust bindings as an external project. Paddle documents ONNX inference/export routes, but a runtime executing a model does not implement detection postprocessing, crop rectification, recognition decoding, or reading-order recovery. A Rust wrapper over a native C/C++ inference library is also different from a completely Rust neural runtime. [ONNX Runtime community APIs](https://onnxruntime.ai/docs/get-started/community-projects.html), [Paddle inference engines](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/inference_deployment/local_inference/inference_engine.en.md), [Paddle ONNX export guidance](https://paddlepaddle.github.io/PaddleOCR/main/en/version3.x/deployment/obtaining_onnx_models.html).

A minimal Rust port should begin with one pinned text detector and one Vietnamese-capable CTC recognizer, not all seven PP-Structure modules. Match the reference engine on image channel order, interpolation, normalized tensor values, stride padding, detector thresholds, contour expansion, perspective crop coordinates, recognition width handling, CTC blank/repeated-token behavior, Unicode dictionary order, and score aggregation. Preserve tests comparing intermediate tensors/boxes and final text on the same inputs. Adding a layout detector also needs class maps, box scaling, overlap handling, and reading order. Table reconstruction, dewarping, stamp recognition, handwriting, and formula recognition are separate milestones. Paddle's current JavaScript architecture is another official example of a non-Python pipeline composing OpenCV and ONNX Runtime, not evidence that those operations have already been implemented in Rust. [Paddle JavaScript architecture](https://github.com/PaddlePaddle/PaddleOCR/blob/main/paddleocr-js/docs/architecture.md).

For the first extraction implementation, the proposed processing sequence is:

1. Ingest a bundle manifest and keep each original file, SHA-256, media type, page count, and original page index. A file is not automatically a document boundary, and several files are not automatically one contract.
2. Produce a page overview for classification while retaining a higher-resolution source for selective crops. Apply EXIF orientation and record every render/rotation/resize transform. A scan physically photographed sideways without EXIF may still need orientation classification; EXIF correction does not solve perspective distortion or page curl.
3. Classify pages as contract opening/body/signature, identity front/back, addendum, receipt/other, or unknown. Permit uncertain classifications. Detect two cards or a card and contract on the same page as separate regions rather than assigning the whole page to one type.
4. Group pages into logical documents using page order plus observed continuation cues, document headings/numbers, repeated names, and card front/back cues. Preserve uncertain boundaries. An identity attachment is associated with a candidate person only after matching actual observed attributes; position after a contract is insufficient.
5. Obtain text and geometry from the chosen local OCR/layout path. For digital PDFs, a verified text layer can provide candidates efficiently, but compare against rendering when the layer is empty, displaced, or inconsistent. Keep text-layer and OCR observations distinguishable.
6. Ask Qwen for field candidates within each document or relevant page group. Supply stable page/region IDs and source text, plus selected images where visual disambiguation is necessary. Separate observed strings from normalization. Document text is data, never instructions; the extraction step has no tools or external actions.
7. Re-read small, ambiguous, or critical candidates from the original-resolution region. Preserve nearby labels and sufficient surrounding context so a date is not confused with a different date or an ID with a phone number. Overlapping crops must not create duplicate fields. Cropping an already reduced 2048-pixel page cannot recover discarded glyph detail.
8. Validate every returned reference and value in Rust. Require evidence for positive observations, normalize only through named rules, retain all conflicting candidates, and derive a review status. Do not allow the model to directly decide that a field is verified.
9. Reconcile contract candidates with identity attachments and produce an application result. Keep observed contractual role separate from observed identity-card ownership. A discrepancy produces a conflict, not a silent overwrite.
10. Persist stage/version metadata and resumable artifacts privately. Include schema, prompt, model checkpoint/revision/quantization, detector/recognizer, transforms, and processing settings. A worker restart should reuse immutable successful stages where safe, with the existing lease fencing applied to final state changes.

Classification, grouping, and candidate association are proposals that need local evaluation; they are not asserted capabilities of the current worker or any individual OCR model.

The proposed application schema has three levels: bundle, document, and field observation. The bundle contains files/pages, logical documents, links between documents, extraction versions, and review status. Documents preserve their type and page membership. Each field contains all observed candidates and a separately selected normalized value. This avoids reducing a front/back identity card and several contract pages to a single flat record.

For rental contracts, candidate fields can include agreement number and signing date; landlord/tenant names, identifiers, contact/address strings; property address; start/end dates; rent amount, currency, payment interval, deposit, due-day expression; and signatory observations. For identity attachments, capture document type, full name, identifier, birth-date string, and other explicitly requested printed fields. Distinguish a visible signature region from a conclusion that a signature is legally valid, and distinguish a printed identity value from authentication of the physical card. These are extraction fields, not legal or identity verification.

The following is a synthetic design example, not data from a user's document. References must be checked against artifacts created by the system; the model cannot invent a new region ID and have it treated as evidence.

  "documents": [

      "document_id": "contract-1",
      "type": "rental_contract",
      "pages": [1, 2, 3],
      "fields": {
        "monthly_rent": {
          "status": "candidate",
          "selected_candidate_id": null,
          "normalized": null,

                  "file_id": "file-1",

A field state should distinguish at least `candidate`, `accepted`, `missing`, `unreadable`, `ambiguous`, and `conflicting`. `missing` means the relevant source does not provide the field; `unreadable` means a likely value exists but cannot be read reliably. Both use a null normalized value. A numeric `0`, empty ID string, or fabricated default must not represent either state. User confirmation or a calibrated automatic policy can select a candidate; extraction alone cannot.

Spatial evidence belongs in an immutable artifact record: original file/page, rendered page dimensions, coordinate origin/units, polygon or rectangle, crop ID/hash, transforms to the original page, OCR/model version, and text. Represent page and crop coordinate systems explicitly. Normalized `[0,1]` coordinates, rendered pixels, PDF points, and bottom-left/top-left origins cannot be mixed. A Qwen-generated rectangle is a proposed localization; a detector-derived rectangle is a measured model output, but it too can be wrong. Neither should be labeled exact ground truth.

When only the existing full-page Qwen strategy is available, return page-level evidence and `bbox: null` rather than manufacturing boxes. The quote establishes traceability to the generated transcription, not independently to the source image. Critical fields still require a local re-read or human comparison with the actual page. Matching a candidate to the same model's own OCR text does not independently establish correctness.

For schema-controlled generation, current vLLM supports `structured_outputs: {"json": schema}` and OpenAI-style `response_format` JSON schema. Older `guided_json` fields were removed in vLLM 0.12. Use the installed server's documented supported subset and a deliberately simple schema; test unions/nulls, required properties, arrays, enums, and additional-property restrictions against the exact backend. `finish_reason: "length"` remains incomplete even if a parser happens to accept a prefix. JSON parsing, schema checking, and Rust domain validation are separate gates. [Current vLLM structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/).

A grammar constrains which strings may be generated. It cannot determine that a visually ambiguous digit is correct, identify the right person, or prove the quoted amount is the monthly rent rather than a deposit. If a schema requires a non-null ID without providing an unknown option, it can pressure the model into returning a syntactically valid invention. Include nullable values and explicit uncertainty states, and reject evidence references outside the provided page/region set. Schema validity is a formatting check, not semantic accuracy.

Rust validators should be narrow and traceable. Preserve raw strings and apply Unicode NFC before comparison, without stripping Vietnamese accents from the canonical value. Use string representations for identifiers so leading zeros survive. Validate digit-only/length constraints only for an identified document type and the application's configured rules; legacy identifiers and other document types must not be forced into one length. Do not silently replace `O` with `0`, or repair one person's identifier using another attachment.

For dates, parse the observed format explicitly and retain ambiguous forms. Compare end/start dates, and distinguish signing date, lease start, birth date, and identity issuance date through labels and context. For money, preserve the raw separators and written currency; parse into decimal/integer units using explicit locale rules, never binary floating point. Compare amounts written in words and digits as a consistency check; disagreement creates a conflict. Keep rent, deposit, utilities, and total obligations separate. A plausible-looking amount or date is still not proof it was read correctly.

Conflict handling needs source priority rules agreed for the application. A later addendum may amend a rent value, but date order alone does not establish which terms govern. Return the conflicting sources and reason for review instead of making an unrequested legal interpretation. Name/identifier matches can support document association; fuzzy name similarity alone cannot identify a person. Multiple cards, spouses/co-signers, repeated template text, stamps crossing text, and handwritten edits deserve dedicated review rules.

Confidence should initially be an evidence/risk record, not one unexplained percentage. Store available image-quality signals, detection/recognition scores, token-logprob summaries, duplicate/cross-document agreement, exact-match grounding, format checks, and conflict flags separately. An OCR recognition score is not document classification confidence; either is different from field correctness. A confidence number written by Qwen is generated text and must not be accepted as calibrated probability.

Current vLLM distinguishes raw and processed logprobs, with `raw_logprobs` documented as default. Processed values reflect logit processors and sampling settings. Grammar masking can greatly restrict the available alternatives, so a high conditional token probability may reflect the constraint rather than strong visual evidence. Raw logprobs are also model token likelihoods, not a measurement of factual correctness. Record the mode, tokenizer, checkpoint/quantization, and constraint configuration before comparing scores. [vLLM logprob modes](https://docs.vllm.ai/en/latest/configuration/engine_args/).

Do not multiply every JSON token's probability and call the result field confidence: punctuation, repeated keys, string length, and tokenization distort it. A Vietnamese name may use more tokens than a familiar English name. Long addresses naturally accumulate more uncertainty than short numbers, and a constrained identifier grammar excludes alphabetic alternatives even when the image is unreadable. Repeated calls to one model can share systematic errors; agreement is a useful signal, not independent verification.

Calibration requires labeled local outcomes. The neural calibration literature motivates measuring whether confidence tracks accuracy, but it does not prove that a Qwen/Paddle score is calibrated for this workload. Semantic entropy research addresses a subset of inconsistent/confabulated generations; it does not certify consistent OCR misreads. Use held-out field labels to learn or calibrate a risk score, then select review thresholds according to observed precision/coverage and the cost of mistakes. Recalibrate after model, preprocessing, quantization, dictionary, schema, or prompt changes. [Calibration paper](https://arxiv.org/abs/1706.04599), [semantic entropy study](https://www.nature.com/articles/s41586-024-07421-0).

The review interface should present the candidate value, relevant label/context, source page, highlighted crop, competing observations, and validation findings together. Reviewers should be able to mark unreadable/missing, correct a value, associate an attachment, or reject a grouping. Persist their correction and evidence independently from model output. Do not replace an observed value silently after review, and do not treat a review acceptance as a claim that the underlying contract or card is authentic.

Golden evaluation should measure the complete application outcome, not just the prettiness of Markdown. Start with a consented local corpus spanning contract templates, identity formats, printed/handwritten changes, front/back combinations, several cards on one page, separate files versus one PDF, phone rotation/perspective/blur/glare, weak Vietnamese diacritics, low contrast, crossed-out values, duplicated pages, missing pages, and conflicting addenda. Include pages that contain no requested fields, unrelated attachments, blank pages, and visible prompt-injection text.

Split the corpus by person, contract/template source, and scanning session where possible. Pages from the same agreement or synthetic variants of one card must not leak across training/calibration/test partitions. Keep a blind test partition and label raw values, normalized values, page/document membership, field roles, evidence regions, unreadable/missing cases, and conflicts. Two annotators plus adjudication for difficult critical fields provide more defensible ground truth than one automatic judge.

Compare at least these configurations using the same corpus and hardware: current Qwen full-page Markdown then text extraction; direct Qwen schema extraction; a Vietnamese-configured spatial OCR/layout pipeline then Qwen extraction; and localized re-reading for uncertain fields. GLM-OCR direct KIE and PaddleOCR-VL region parsing can be additional measured candidates. Keep exact model versions and resource budgets fixed when comparing. Public document-parsing leaderboards and recognition metrics do not rank these complete application strategies on Vietnamese bundles.

Report field-level exact match for identifiers, dates, and amounts; accent-preserving name/address metrics; false positive rates on absent fields; unreadable/missing distinction; landlord/tenant assignment accuracy; document-grouping/attachment-association errors; evidence validity and localization overlap; conflict recall; and precision among automatically accepted fields at each coverage level. Also report bundle-level all-critical-fields-correct rate, review rate/time, retries/truncations/failures, cold/warm latency, throughput, and peak memory. A global average hides one unreliable critical field.

Report denominators and uncertainty intervals alongside accuracy. A tiny clean sample with no observed mistakes is insufficient evidence of a low production error rate. Bootstrap at the bundle/person level rather than treating correlated pages or repeated fields as independent cases. Select policy thresholds on the calibration partition and report their resulting precision/coverage once on the held-out test set; repeatedly tuning on that test set removes its independence. Keep separate results for supported templates/languages and unfamiliar inputs so good performance on easy contracts does not conceal failure on identity attachments or handwriting.

An initial rollout can return candidates for every bundle and require human review for critical identifiers, rent, deposit, dates, and party assignment. Once the held-out corpus demonstrates the application's required error rate, permit selective automatic acceptance for supported, grounded, conflict-free fields under a versioned policy. There is no defensible universal `confidence > 0.9` rule without those measurements. Stop automatic acceptance if drift or critical-error monitoring crosses the agreed threshold.

Operationally, model downloads and public research access are separate from document processing. Pre-download pinned model artifacts, use explicit local inference URLs, disable unwanted telemetry and remote fallbacks, and restrict runtime egress. Log job/stage IDs and aggregate metrics rather than names, identifiers, raw OCR text, or image bytes. Keep originals, crops, OCR artifacts, and review corrections under the same private access and retention policy; adding evidence artifacts increases the amount of sensitive data stored. These choices follow the user's local-processing requirement and should be part of the implementation design.

The implementation order should be modest: define the bundle/field/evidence contracts and golden corpus; add candidate extraction and Rust validation to the existing Qwen baseline; add real spatial OCR and selective original-resolution crops; then evaluate alternative layout/OCR models and calibrate review decisions. Avoid porting complete PP-Structure or swapping models before measuring where errors occur. The first meaningful success is a correct field with inspectable evidence and an honest uncertainty state, not merely a valid JSON object.
